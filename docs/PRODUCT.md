## 1. 产品判断

一句话：每个人选自己想吃的，一起确认一份真实可买、分账清楚的麦当劳餐单。

首要用户是 2—6 人的同事午餐、朋友小聚、宿舍点餐。一次流程聚焦一个门店、一个取餐场景、一位付款人。发起人最麻烦的不是计算器不够聪明，而是收集意见、追问“随便”的含义、修改套餐后再次沟通，以及最后算钱。产品应减少这些往返。

核心价值顺序：偏好不丢失 → 每人预算受尊重 → 方案可解释 → 大家同意 → 真实核价与交接。节约金额是结果之一，不作为唯一目标。不承诺全菜单最低价。

### 与相近作品的区别

2026-10-18 抽查：套餐拼图已有组合与分餐；麦麦辩论局已有共享房间和 Agent 辩论。不能把“多人点餐”本身当作独有创新。合拍将重点放在每人独立表达、受影响成员重新确认、版本一致的清单与分账上。最终竞争力需要真实体验证明。

## 3. 角色和权限

**发起人**：创建房间，选门店与取餐方式，设置结束时间，邀请成员，提出方案，最终核价并创建订单。不能代替真实成员确认支出。也作为普通参与者拥有自己的餐盘。

**成员**：用邀请链接进入，设置昵称与个人偏好，修改自己的餐盘，确认或拒绝当前方案。只能编辑自己的数据。自己的预算默认只对自己与计算服务可见；其他成员可见最终餐品和分摊金额。

**演示体验者**：在本地演示页面切换样例角色，了解协作过程。页面明确写“单机演示”，不能把角色切换当成真实身份认证。

## 4. 主流程

1. 发起人创建房间，选择门店/到店自取，获取有效菜单快照。
2. 分享邀请链接。成员输入昵称即可加入，不要求每个人都配置 MCP Token。
3. 成员完成偏好卡：预算、主餐、饮料、薯条偏好、是否接受共享。提供表单；自然语言是后续增强入口。
4. 成员提交后，发起人生成有限候选。候选必须遵守成员硬约束，再依据软偏好排序。
5. 返回最多三套不同方案：预算优先、心愿优先、适合分享。没有足够不同方案时只显示实际数量。
6. 每套方案显示餐品归属、分摊明细、未满足的软偏好、报价来源与时间。查看方案不等于选中或同意。
7. 发起人提出一套方案，成员逐一确认。提出修改、成员增减或重新核价导致金额变化，都生成新版本并清空确认。
8. 全员确认后，发起人重新核价。与已确认内容一致且有效时，确认建单；变化则回到确认阶段。
9. 官方返回支付链接后由付款人完成支付。订单查询与支付状态以官方能力为准，不能把链接已打开当成支付成功。
10. 输出最终清单与分账卡。项目不托管资金、不代收分账。

## 6. 关键业务规则

### 6.1 硬约束与软偏好

硬约束：各付各的模式为每人预算上限，请客模式为整桌预算上限；明确必选项、明确排除项、套餐选择规则、成员身份、门店可用性、同一账户优惠规则始终适用。无法满足就返回冲突，不擅自提高预算或修改口味。

软偏好：有则更好、愿意尝试、愿意共享。首版先用透明计数解释满足情况，不展示未经验证的“AI 幸福指数”。

普通口味排除与医学过敏需要区分。官方数据未充分支持时，不能声称系统能保证无过敏原或无交叉接触；首版不把它包装为过敏安全判断功能。

### 6.2 共享与优惠

只有主动同意共享的成员参与共享项目。实际谁吃哪项，决定谁分摊。个人项目默认本人承担。

请客模式保留餐品归属与餐品价值分摊，但最终应付全部由请客人承担，其余为 0。餐品金额合计与应付合计都需等于整桌金额；个人预算暂停参与筛选，改用整桌预算，请客人仍要确认。

首版使用单一付款账户，不能合并其他成员账户里的券。优惠分配策略需在选方案前可见：商品级优惠归该商品的承担者；订单级优惠按符合条件的折前金额比例分摊；无法确认适用范围则不自动分配，要求选择一种全员认可的规则。

配送/包装等费用必须纳入总额。首版真实模式先收敛到到店自取，仍须检查接口是否返回附加费用。

金额始终使用整数分。尾差使用最大余数法；相同余数按稳定成员 ID 排序。应付不能为负，合计必须守恒，分摊后再检查每人预算。

### 6.3 方案与确认

每次影响餐品、份量、归属、费用或参与人的变化，生成新的 proposalVersion。首版采用全员重新确认，简单可靠；后续再设计仅受影响成员重确认。

偏好变化后旧方案保留为历史，但立即标记过期并不可确认。报价过期后进入重新核价，不能继续下单。真实供应商有效期若缺失，采用产品自身短期展示时限并说明这不是价格保证。

### 6.4 无解、掉线与异常

无解：保留用户原始约束，显示可行的调整方向，只有本人确认才生效。

掉线：成员可恢复会话，恢复后取最新版本；不得在离线期间自动同意。

门店/时段/套餐变化：清理受影响候选和报价，展示原因。全员未到齐不假装协作完成。

建单超时：标记结果未知并尝试查询，不能盲目重复建单。

## 7. 页面与交互

1. **房间首页**：当前门店、成员状态、进度、邀请。
2. **我的偏好**：一屏完成常用输入，预算放在明显位置。
3. **共识餐桌**：三套方案对比、我的餐盘、共享盘、报价说明。
4. **确认清单**：逐人列出金额与状态，“我同意这份餐单”。
5. **结果页**：订单交接状态、可复制分账清单、再开一桌。

视觉：奶油白、番茄红、炭黑与少量黄色；桌面像围坐餐桌，手机先展示自己的卡片。使用原创图形，不将页面伪装成麦当劳官方产品。所有图标按钮需有可读名称，表单支持键盘，状态不只靠颜色。

## 8. 当前原型边界

当前已搭建单机交互原型与可测试领域层：演示菜单、2—6 人自选、偏好编辑、生成候选、按人分账或请客、匿名投票交互、约束内随便主餐、切换角色确认、改动撤销确认、默契小票 SVG、固定饭搭子本地模板。角色切换用于演示，多台设备还不会共享房间或隔离私密选票。

## 10. 同城饭搭子：从认识朋友到一起吃饭

目标入口分为“和朋友合拍”与“同城找搭子”。朋友入口保留已有餐桌；切换入口保留页面内餐单状态。同城匹配首先匹配饭局，双方明确同意后再建立成员关系，不直接把陌生人塞进餐桌。

### 功能闭环

1. 用户登录麦麦合拍，设置昵称、城市、常去商圈、聊天节奏和主动填写的口味偏好。找搭子不要求绑定麦当劳账户。
2. 发起饭局：具体日期、起止时间、商圈、2—6 人总名额、建议人均预算区间、下单方式、截止时间。发起人占一个名额。
3. 寻找饭局：同城、时间交集、商圈、空位、预算交集、下单方式是筛选条件；口味与聊天偏好用于排序，展示具体理由，不编造“灵魂契合率”。
4. 申请加入：发起人同意才入房；申请时不占正式名额。接受申请时服务端再次检查容量、截止时间、拉黑关系及申请状态，在事务内增加成员，防止多人抢最后一个位置。
5. 共同确定公开门店 → 各自选餐 → 全员确认当前版本 → 进入各自下单或协商代付流程。加入饭局不等于付款承诺。
6. 餐后双方主动添加“固定饭搭子”，未来可再次邀请。单方收藏是私有书签，不能当成对方已加好友。
7. 随时撤回申请、拒绝、退出；退出导致餐单版本失效。提供拉黑、举报与处理记录；陌生人沟通先限于已接受的饭局房间。

发现页只公开昵称、主动公开的商圈/时间/偏好及饭局名额。不公开手机号、麦当劳资产、支付链接、取餐码、家庭地址或连续定位；不根据相同学校位置推断学生或已认证同学。正式版需对垃圾申请、骚扰和举报提供服务端处理能力。

### 两种下单方式

| 方式 | 账户与费用 | 适用场景 |
| --- | --- | --- |
| 各自下单，一起吃（同城默认） | 每人授权自己的麦当劳账户，分别使用自己的券/会员权益并支付自己的订单 | 新认识的搭子；集合多个官方订单，不合并跨账户权益 |
| 一人代付，再分账 | 选定付款人，使用该付款账户的券/会员权益形成一单；其他人无需授权麦当劳账户即可参与选餐 | 朋友局或双方明确同意的饭局；付款人承担整单，应用仅出分账记录 |

“我请客”属于后一种：请客人承担整桌金额，不向成员收款。应用的分账清单不是官方多人支付；当前公开工具中未发现一单拆成多人付款、平台代收后自动结算的能力。各自下单的独立订单可能一个成功、另一个失败，页面要分别报告，不能承诺原子支付。

### 当前可评审原型与下一阶段

已提供城市/商圈/日期/时间段/预算/人数/付款方式筛选，偏好排序与推荐理由、申请/撤回、模拟对方同意或婉拒、饭局草稿和演示收藏。样例人物全部虚构；没有真实社交数据、跨用户通讯或公开发布接口。模拟操作与真实点餐明确隔离。

新增“发布找搭子 / 我的发布”：标题、发起人昵称、城市、公共商圈、未来用餐日期及固定时段、总人数（2—6，含发起人）、人均预算上下限、下单方式、标签。必填、日期、金额精度与范围均校验，不接受预算倒置。人数初始为 1，自己的饭局不可申请；发布成功后可主动按该饭局条件跳到列表查看，不静默改变原筛选条件。

发布已保存到本机 SQLite，最多 20 条；旧浏览器记录按 ID 迁入，数据库记录优先且原浏览器数据保留。支持编辑、关闭、重新招募及重启恢复，事务内拒绝过时覆盖。到用餐开始时标记过期并从推荐移除；过期饭局需修改为未来时间才能重新招募。编辑关闭饭局不会擅自重新开放。当前为本机单所有者工作区，没有真实报名，不能模拟成已经有人报名。

正式版仍须接入应用账号和带权限的多人房间，扩展现有数据库，再开放真实发布与匹配。顺序是：真实朋友邀请房间 → 小范围同城饭局 → 受控订单交接。首轮采用到店自取，先把多人协作和账户隔离跑通。

## 11. 麦当劳账户与官方支付交接

本机个人授权现已实现：在官方开放平台登录获取 Token，再在账号面板连接；也可验证既有环境授权。成功后加密保存到 SQLite，支持重启恢复、重新验证和断开；失败不替换旧连接，更换账号重置餐单。此功能不是第三方 OAuth 登录，也没有开放跨用户共用账号。详见 LOCAL_RUNNING.md。

2026-10-19 核实：官方文档说明 create-order 返回订单和支付链接；本机 tools/list schema 含 data.payH5Url、orderId，query-order 提供订单状态和支付截止时间。官方建议通过支付链接扫码或麦当劳 App 完成支付。没有执行建单来验证具体支付渠道、页面兼容性和回跳行为。

目标流程：本人明确确认付款人/门店/取餐方式/完整餐单/金额 → 最终核价且与已确认版本一致 → 创建订单 → 展示官方返回的支付链接 → 用户在官方支付页操作 → 查询官方订单状态 → 展示已支付与取餐信息。打开链接、切回网页、点击“我已支付”都只能触发查询，不能直接标记支付成功。

两个账户体系须分开：应用账号负责社交与房间权限；麦当劳授权负责对应账户资产和订单。现有开发 Token 已用于访问账户券与核价，不代表产品已支持其他用户登录。公开文档介绍“官方平台手机号验证登录 → 申请 MCP Token → Bearer Token 调用”，尚未查到可用于第三方网站的一键 OAuth/微信登录协议，不自行仿造麦当劳登录表单或收集密码、短信验证码。

当前无需用户再配置 Token。正式多用户接入前需确认官方允许的授权与凭证托管方式；单用户演示可继续使用本机 Token。公开站点不得共用开发者 Token，麦当劳凭证仅服务端按授权用户隔离。每个订单只用所属付款人的凭证，支付链接只对该订单付款人可见。
