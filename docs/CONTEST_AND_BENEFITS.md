## 1. 作品以什么形式存在

推荐交付：手机与电脑都可使用的响应式 Web 应用 + 服务端 MCP 适配 + GitHub 开源仓库。

- 用户入口：浏览器中的“麦麦合拍”餐桌。目标流程是发起人分享链接，成员加入、填偏好、投票、确认，付款账户通过官方能力完成核价和订单交接。
- 运行结构：浏览器处理交互，服务端处理成员权限、数据库、组合推荐与 MCP 调用；Token 不进入浏览器。
- 参赛提交物：公开 GitHub 仓库，附可运行代码、安装步骤、例子、集成说明及官方要求的声明文件；在线体验地址和视频有助于展示，但不是这里核对到的硬性提交要求。
- 可选增强：后续补一个可在 WorkBuddy 使用的对话 Skill，共用应用服务。比赛并未要求一定交付特定 SKILL.md 包、微信小程序、原生 App 或自行实现 MCP Server。

官方规则将 Skill 范围覆盖到应用程序、智能体、插件及自动化流程等。以上 Web 方案符合规则描述的作品形式，最终资格仍由主办方审核。它必须真实使用麦当劳 MCP，单纯演示页或只写集成计划不够。

官方要求的仓库内容：README.md、原样 CONTEST_DECLARATION.md、MCP_INTEGRATION.md、仅环境变量占位符的 mcp-config.example.json，以及可运行主体代码。参与 WorkBuddy 专项奖励需真实使用 WorkBuddy，并提交真实的 workbuddy.md。

## 2. 新定位：一起选餐，也一起把优惠用对

把大家分别想吃的餐品汇总成需求清单，再比较普通单点、普通套餐、账户优惠券、账户实际可用的麦金卡套餐。多人“合拍餐桌”是一个协作会话；底层能否合成一张官方订单，取决于官方核价和渠道限制，不预先承诺所有券都能叠进一单。

例如：甲想吃鸡肉堡，乙想吃牛肉堡，丙需要咖啡和薯条。系统先查询可用券及套餐内容，尝试“券套餐覆盖部分需求 + 少量单点补齐”，检查每个人拿到什么、有无多余餐品、是否超预算，然后请求官方核价。套餐仍需作为合法完整商品购买；给成员分配套餐内餐品只是分餐，不能把套餐拆成官方不支持的独立优惠单品。

## 3. 第一阶段：麦当劳账户内可用券

已核实官方文档列出：

| 工具 | 在本项目的用途 |
| --- | --- |
| query-my-coupons | 获取当前授权账户的可用券概览 |
| query-store-coupons | 查询当前门店可用券，以实际门店/就餐上下文进一步判断 |
| query-meals | 读取当前可售菜单及接口实际返回的优惠价信息 |
| query-meal-detail | 获取套餐组成与合法替换项 |
| calculate-price | 对含券的候选请求官方金额、优惠与应付总价 |

来源：[麦当劳 MCP 官方工具清单](https://github.com/M-China/mcd-mcp-server/blob/main/README.md)。本阶段已依据实际 tools/list 与调用实现，字段与联调结果见 [MCP 集成记录](../MCP_INTEGRATION.md)。未验证的券次数、叠加条件和错误场景仍不能从工具名称推测。

首版只用一个授权下单账户的权益。成员不用为了填写口味都配置 Token；有券的成员和付款账户不是同一账户时，不假设券可转让或跨账户拼接。

界面新增“本桌优惠”区，显示券名、适用商品、门店/时段限制、期限、数量与状态。未知字段明确显示“待核实”，不补造；默认只有本桌授权账户实际可用的券能参加官方候选核价。

展示三类状态：待核实 / 当前不可用（含原因）/ 当前条件下已核价。看到券或看到商品优惠价，不等于整套组合已经核价通过。

查询可领券和实际领券分开。首版先读账户已有券；后续提供明确“领取可领券”操作时才调用 auto-bind-coupons，生成方案本身不隐式领券、兑换、购买卡券或下单。

## 4. 麦金卡作为权益来源

官网介绍的麦金卡权益包括专属套餐和满足条件的外送费优惠，并明确适用门店可能不同；具体以官方 App、小程序权益页和接口实时结果为准。不要硬编码长期固定的套餐价、卡价、每天使用次数或统一折扣率。

官方 MCP 更新日志提到支持优惠价格展示及随单购买麦金卡/早餐卡。这能说明相关场景存在，但不能证明任意账户的持卡状态、所有权益或全部套餐替换项都已完整开放。

2026-10-19 实测菜单返回 discountType="麦金卡优惠"，热美式中杯官方核价 990 分、大脆鸡扒麦满分套餐 1140 分；前者与一份券套餐及一份脆薯饼同请求核价为 2780 分。仅代表该测试账户、门店和早餐时段，不据此生成会员卡有效期或全量权益状态。菜单另有 canWithOrder=true 的随单购卡优惠，本轮不启用，不传 withOrder。

来源：[麦当劳持卡权益介绍](https://www.mcdonalds.com.cn/index/Services/cards-and-benefits)、[官方 MCP 版本日志](https://github.com/M-China/mcd-mcp-server/blob/main/README.md#4-版本日志)。

产品规则：

1. 以当前授权账户实际返回的权益商品、资格和报价为依据。无法验证持卡状态时显示“未核实”，不把用户勾选“我有卡”当作可使用会员价的证据。
2. 先接入已持卡用户可用权益。若接口只返回可售套餐及优惠价而不返回持卡状态，可展示“账户下当前已核价套餐”，不强行生成一个持卡状态。
3. 麦金卡套餐是候选餐品组合；有券不代表在会员价基础上还可再减一次。会员价与券是否兼容交给官方核价确认。
4. 不默认随单买卡。如果后续提供“买卡后是否划算”的比较，必须单列买卡费用、当单可享权益与权益生效条件，用户明确选择后才进入购买流程。
5. 当前聚焦到店自取，外送费权益先不计入这一模式的节省金额。

## 5. 优惠组合与单点补齐

```text
成员需求 + 预算 + 排除项
             ↓
当前账户 × 门店 × 就餐方式 × 时间
             ↓
可售单品 / 合法套餐 / 账户券 / 已核实会员权益
             ↓
有限候选：覆盖需求 + 单点补齐 + 餐品分配
             ↓
官方核价与可用性校验
             ↓
最多三套方案 → 投票 → 全员确认 → 最终核价
```

- 排序先满足硬约束，再考虑实际支付、可选心愿、额外餐品及操作复杂度；不为凑优惠强塞餐品，不承诺全局最低价。
- 每张券保留独立身份与使用次数，不能在同一候选里重复使用同一个券实例。
- 互斥或叠加规则未知的组合只作为待核价候选；核价失败后列出失败原因并移除，不能显示成“已省”。
- 若券或套餐要求各自下单，则作为后续多单执行清单，逐单报价、逐单确认和跟踪；不能暗中拆单，也不能把多单包装成一笔支付。本阶段不自动执行多单。
- 比价必须是同一账户、门店、时段和可比较餐品；没有可比基准时只报总额，不显示虚构的节省金额。餐品不同的候选明确注明差异。
- 修改用券、会员套餐、下单账户、门店、分餐或最终金额，都会使原投票与确认失效。

## 6. 团购券和已经付过的钱

后续支持抖音、美团等第三方团购券，但先验证是否能进入当前麦当劳账户并被官方接口识别。官方公开清单未明确提供任意第三方券码通用核销能力，因此不能承诺在本项目里直接核销所有平台的券。

第一步可以手动登记套餐内容、来源、购买金额、有效期和限制，作为“待核实搭配草稿”；不要求上传有效券码。识别不完整或未验证的券不能混入已核价官方订单。无法通过 MCP 使用时，保留原平台/官方渠道操作步骤，由用户完成核销。

必须区分三个数：

- **本次新增支付**：官方当前应付，加上本次新购买的卡/券等成本；不能遗漏同流程发生的额外购买。
- **已购券消耗成本**：此前购买并在本餐消耗的券成本。未知时标记未知，不能填 0。
- **本餐计入总成本**：已知的券成本 + 本次新增支付，且不重复计入已包含在官方总额内的费用。

例如：已购券花了 39 元，本餐还需补单点 12 元，则新增支付 12 元、本餐计入成本 51 元。若是多人分账，需要明确券由谁出、是否将这 39 元计入分摊；不能只分摊新增的 12 元后声称已结清整餐。

首版预算默认按本餐计入成本检查，界面另列本次现金支出；用户若选择只限制本次新增支付，需明确展示该口径。请客模式也须明确已有券的提供者及承担方式，不沿用隐含的付款承诺。

已有麦金卡的历史购买费不自动按每餐摊销；页面说明比较的是本次边际支出。若本次新买卡，则当次购卡费用必须列入比较，不能只看折后餐价。

## 7. 领域与服务端的增量设计

以下是本项目内部模型草案，不是 MCP 请求参数：

| 模块 | 职责和关键数据 |
| --- | --- |
| BenefitSnapshot | 账户隔离引用、门店/时间/方式、抓取时间、券实例和状态、证据来源 |
| BenefitOffer | 官方券/会员套餐/第三方预付券；额度、适用品、限制、预付成本、可用性证据 |
| BundleCandidate | 官方合法套餐结构、替换项、每份餐品的成员归属、额外餐品 |
| QuoteRequest | 上下文、候选餐品、候选权益、配置版本；由适配器映射真实 schema |
| VerifiedQuote | 官方应付、明细、优惠、额外费用、实际采用权益、报价时效及请求内容哈希 |
| MealCostLedger | 本次新增支付、已购券消耗、提供者、分摊/请客规则、成本口径 |
| BenefitPlanner | 生成有限可行候选、避免重复用券、统一核价和过滤，不自行宣布可叠加 |

套餐分餐采用官方明细价；接口没有组件价时，用事先公开并全员确认的分摊规则，不把自行分摊额标成官方单品成交价。

Token 只在服务端使用。公共房间不返回完整券码、会员身份信息、Token 或账户原始响应；仅显示这份餐单必要的优惠名称、适用状态和金额。
